### 1.2 审查维度

每个模块都按以下五条风险轴逐条核查，报告中的"五轴核查"行记录每一轴是否核查通过：

- **A 金额与结算**：折扣/券/满减/佣金/餐补/退款/提现/对账的计算口径是否唯一；是否有 `double`/`float` 参与金额运算；分摊是否产生分币误差或负数；退款是否按实付而非原价。

## 二、总体结论

**一句话**：这个项目的工程质量明显高于同规模个人项目（金额一律 BigDecimal、大量原子 UPDATE/CAS、分布式锁与幂等键已成习惯），但风险不在"某个算法写错"，而在三类横向错配：**事务边界**、**权限粒度**、**"先查后写"缺数据库兜底**。修这三类模式，比逐条改 126 个点更省力。

发现最密的三组是资金结算（21 条）、平台账号（16 条）、会员营销（14 条）；最少的是订单支付（6 条）与公共基础层（6 条）——但这两处的"少"性质不同：订单支付是真的做到了（分布式锁、累计退款上限校验、状态 CAS 都在），公共基础层则是文件少、每一条都是横切影响。

### 2.2 最该先看的三件事

1. **1 条 P0 在 AI 供应商配置**：`/admin/ai/provider` 整个 Controller 只有类级 `@RequireEmployee`，`get/{id}?reveal=true` 直接返回明文大模型 API Key，`add/update/delete/activate` 也没有超管限制。任意门店员工（含收银、骑手管理员）都能拿到密钥并改计费供应商，后果是按量计费的账单被盗刷或记到错误主体。
2. **"状态改了、权限没改"贯穿三个域**：员工停用、顾客封禁、租户停用/过期，三处都只改数据库状态，既不失效既有 `HttpSession`，也不吊销 `X-Auth-Token`（TTL 72 小时），而 `LoginCheckFilter` 三个分支（员工/顾客/token）都不回查主体状态。也就是说"把人踢下线"这个动作在当前实现下没有强制力。
3. **事务里做外部调用、事务提交前发事件**：`DeliveryServiceImpl.acceptOrder` 先在事务内调美团/饿了么接单 HTTP，再回本地做 CAS；`NotificationServiceImpl` 把短信/推送 HTTP 包在 `@Transactional` 里；`OrderStatusFlowServiceImpl` 在事务内 `publishEvent`，监听器是 `@Async + @EventListener`（不是 `AFTER_COMMIT`）。三处都会造成"外部已生效、本地未生效"或"读到事务提交前的旧数据"，且都靠 `catch(Exception)` 吞掉异常掩盖。

### 2.3 金额轴的实际状况（好消息与坏消息）

- 好消息：订单金额主链路（order/payment/cashier/delivery/inventory/dining）全部 `BigDecimal`，在 payment、inventory、dining 三个模块 grep `double/float` 零命中；退款有"累计已退 + 本次 ≤ 实付"的上限校验（`RefundRecordServiceImpl.java:159-163`），提现审批与确认转账都做了 CAS。
- 坏消息：**"金额相等"的判定口径分裂**——退款回调判全额用 `compareTo != 0` 严格等值（`RefundCallbackService.java:151-157`），收银校验实付用 0.01 容差（`CashierServiceImpl.java:760`）。多次部分退款累计出现 1 分尾差时，"全额退款"的联动（支付单转 REFUND、订单转已退款、库存回补）永远不触发。
- 另有两处 `double` 落在报表汇总/排行（`ExportDataServiceImpl` PDF 汇总、`ReportServiceImpl` 菜品排行 int 分），不影响下单金额，但会让"日报"和"明细加总"差几分钱——财务对账时最难解释的就是这种。

### 2.4 状态机的实际状况

做得好的：桌台（`ALLOWED_TABLE_TRANSITIONS` 白名单 + CAS）、库存（`deductStock` 带 `stock_qty >= qty`、`casAdjustStock` 带期望值）、采购单（`receiveFully/receivePartial` 带 CAS）、提现/财务审批（CAS 抢占）、退款单（PENDING→PROCESSING→SUCCESS 全用条件 UPDATE）。

明确缺口的：KDS 工单（无 `@Version`、无 CAS，双击覆盖 `cookStartTime`）、客服抢接（`selectById` 后整行 `updateById`，两人可同时接入）、盘点冲正（只回退状态，不回退库存与流水）、桌台置 FREE（清 `currentOrderId` 但不检查是否还有活跃订单）。

### 2.5 一句提醒

本报告全部结论来自静态阅读，**没有跑过一条测试、没有起过一次服务**。P0/P1 建议按"先写复现用例、再改"的方式推进；标注【疑似，需业务确认】的 21 条，请先找产品或运营对齐口径，不要直接当 bug 修。

### F-category-02 【确认缺陷】P2 修改接口绕过 Service 校验，空更新会生成无 SET 子句的 UPDATE
- 证据：`src/main/java/com/xinfei/module/category/controller/CategoryController.java:143-161`
  ```
  @PutMapping
  public R<String> update(@Valid @RequestBody Category category) {
      LambdaUpdateWrapper<Category> updateWrapper = new LambdaUpdateWrapper<>();
      updateWrapper.eq(Category::getId, category.getId());
      if (category.getName() != null) { updateWrapper.set(Category::getName, category.getName().trim()); }
      if (category.getSort() != null) { updateWrapper.set(Category::getSort, category.getSort()); }
      categoryService.update(updateWrapper);
  ```
- 影响：① 注释写"Service 层已校验存在性、禁止改 type、名称唯一性"，但这里调的是 `update(wrapper)` 而非 `updateById(entity)`，`CategoryServiceImpl.updateById` 的全部校验（存在性、type 篡改、重名、排序冲突）被整体跳过，前端可直接改名成已存在的名字；② 请求体 `{"id":1}`（name/sort 均为 null）时 `set` 一条都不加，MyBatis-Plus 会拼出 `UPDATE category SET WHERE id=?` 的非法 SQL 或抛 `MPGenerateException`，表现为 500 而非友好提示；③ 只按 `id` 定位，未校验 `id` 是否存在，删除后的 id 更新静默成功（0 行受影响也返回"修改成功"）。
- 建议方向：Controller 只做参数接收，改回 `categoryService.updateById(entity)` 走统一校验；或在 wrapper 路径上补齐存在性/重名/type 校验，并在 `set` 为空时直接拒绝。

### F-category-04 【确认缺陷】P3 "今日新增"统计跨日重复计数
- 证据：`src/main/java/com/xinfei/module/category/controller/CategoryController.java:243-247`
  ```

  long todayNew = categoryService.count(
      new LambdaQueryWrapper<Category>()

- 影响：`le` 为闭区间，恰好 `次日 00:00:00.000` 创建的记录会同时计入"今天"和"明天"的新增数，统计卡片在整点附近多算一条。同类写法在其他模块的日统计里可能存在同样的边界问题（`cost`/`report` 组请一并核查）。

### F-category-05 【确认缺陷】P3 批量删除逐条 count+delete，N 条记录 2N 次查询
- 证据：`src/main/java/com/xinfei/module/category/service/impl/CategoryServiceImpl.java:80-89`
  ```

      for (Long id : ids) {
          this.remove(id);
      }

  ```
- 影响：`remove(id)` 内部先 `getById` 再 `count(dish)` + `count(setmeal)` 再 `removeById`，批量删 20 条即 80 次 SQL，全部在同一个事务里持有连接，后台批量清理时容易把连接池打满（HikariCP 默认 10）。正确性无问题（外层 `@Transactional` 覆盖）。

### F-region-01 【确认缺陷】P2 区域树每次请求全表加载并按 O(n²) 重建，且无缓存
- 证据：`src/main/java/com/xinfei/module/region/service/impl/RegionServiceImpl.java:29-45`
  ```
  public List<Region> getRegionTree() {
      LambdaQueryWrapper<Region> wrapper = new LambdaQueryWrapper<>();
      wrapper.orderByAsc(Region::getSort);
      List<Region> allRegions = this.list(wrapper);
      List<Region> rootList = new ArrayList<>();
      for (Region region : allRegions) { if (region.getParentId() == null || region.getParentId() == 0L) rootList.add(region); }
      for (Region root : rootList) { buildChildren(root, allRegions); }
  ```
  证据：`src/main/java/com/xinfei/module/region/service/impl/RegionServiceImpl.java:65-74`
  ```
  private void buildChildren(Region parent, List<Region> allRegions) {
      List<Region> children = new ArrayList<>();
      for (Region region : allRegions) {
          if (region.getParentId() != null && region.getParentId().equals(parent.getId())) {
              children.add(region); buildChildren(region, allRegions);
          }
      }

4. **BigDecimal 判定全额/等值的容差口径不统一**：`RefundCallbackService.applyFullRefundSideEffects` 用 `compareTo != 0` 严格判定全额（见 F-payment-01），而 `CashierServiceImpl.validateActualAmount` 用 0.01 容差（行 760），两处对"金额是否相等"的容忍度不一致。

### 跨模块观察（本组内）

1. **第三方 HTTP 调用混入 DB 事务是 delivery 与 urgency 共有的反模式**：DeliveryServiceImpl 把美团/饿了么同步 HTTP 放在 `@Transactional` 里（F-delivery-01），UrgencyServiceImpl 把短信 HTTP 放在顾客催单事务里（F-urgency-02）。两处都靠 catch(Exception) 兜底不报错，但慢调用/失败时连接持有时间不可控。建议统一抽"事务提交后异步副作用"组件。

### 跨模块观察
1. **"注释说事务外、注解却包着事务"模式**同时出现在 notification（F-notification-01）和 ai（activateProvider:134 在事务内调 reloadConfig 查库——虽不严重但同模式）。说明开发者对 `@Transactional` 的传播边界理解不一致，建议全局 grep `@Transactional` 逐方法确认是否真的需要事务。

### 跨模块观察（≤5 条）

1. **`@EventListener` 全部未用 `@TransactionalEventListener`**：全项目 5 处领域事件监听（common 骨架 + notification/member 业务监听）都是同步发布 + @Async 消费，无一处 AFTER_COMMIT 语义。业务模块新增事件监听时容易复制这个反模式。建议在 common 包文档中显式标注"业务监听必须用 @TransactionalEventListener(AFTER_COMMIT)"。
2. **鉴权切面统一返回 R.error 而非抛异常**：5 个 Guard/权限切面一致采用 `return R.error(...)` 而非抛异常，导致 200 vs 4xx 口径分裂。这是全站口径问题，不是某个模块的 bug。
3. **线程池 TaskDecorator 复制代码重复 5 处**：AsyncConfig 的 4 个 Bean（cacheDoubleDeleteExecutor/recommendExecutor/aiHealthProbeExecutor/exportTaskExecutor）+ EventListenerThreadPoolConfig 的 1 个 Bean，TaskDecorator 逻辑（set currentId/tenantId/traceId → run → finally remove）逐字复制，应抽公共工厂方法。
4. **`@EnumValue` 仅覆盖 Integer 菜品状态**：String 状态枚举（Coupon/Delivery/Reservation/DiningTable）无统一校验注解，业务模块各自 if-else，B 轴状态字面量漂移风险高。
5. **tenant-tables.yml 白名单与代码 fallback 双写**：新增免隔离表需同时改 yml 和 TenantTableRegistry.FALLBACK_IGNORE_TABLES 两处（虽然 fallback 仅在 yml 加载失败时生效），长期会漂移。

## 五、共性模式

以下 8 个模式在多个模块重复出现，**改一处不会消失，需要按模式治理**。每条列出出现位置与统一改法。

### 模式 1：事务边界三类错配

- **外部调用在事务内**：`delivery-01`（平台接单 HTTP）、`notification-01`（短信/推送 HTTP）、`urgency-02`（催单短信在顾客事务内）。
- **事件在提交前发布**：`base-01`（订单完成/取消事件 + `@Async @EventListener`），且 `OrderStatusFlowServiceImpl.java:283-284` 的注释写"事件发布放在事务外由 Spring 保证"——**注释是错的**，`publishEvent` 同步执行，仍在事务内。
- **状态改库但不吊销凭证**：`auth-01`、`tenant-01`、`user-01` 三处同根因。
- 改法：抽一个"事务提交后副作用"组件（`TransactionSynchronization` 或 `@TransactionalEventListener(AFTER_COMMIT)`），外部 HTTP/短信/推送一律走它；状态变更与凭证吊销放在同一 Service 方法里。

### 模式 2：权限只收到"员工"这一层

`@RequireEmployee` 被当成"管理端通用通行证"，于是资金（提现审批、财务审核、发票开具）、封禁（顾客状态）、AI 供应商与提示词、通知模板、客服会话分配全部对任意岗位员工开放。出现位置：`ai-01`（P0）、`ai-02`、`notification-02`、`user-02`、`withdraw/finance/invoice` 系列、`customer-01`。
改法：建立"权限码矩阵"（资金类 `finance:*`、账号类 `user:*`、配置类 `sys:config`），`@RequiresPermission` 覆盖资金与他人数据操作；`@RequireEmployee` 只保留给"本店只读/本店日常操作"。

### 模式 3：先查后写 + 缺数据库兜底

出现位置：`category-01`（重名，注释声称有唯一索引但**库里没有**）、`member-01/02`（券库存、积分）、`marketing-03`（限次记录）、`shopping-02`、`favorite-01`、`address-02`（默认地址）、`attendance`（同人同日）、`customer-01`（抢接）、`urgency-01`（催单限次）、`schedule-01`（排班）、`kds-01`。
改法三选一，按场景：① 业务唯一键建数据库唯一索引（最可靠）；② 条件 UPDATE + 校验受影响行数；③ 分布式锁（`RedisLockUtil` 已具备，仅用于无法建唯一键的场景）。**不要只做 count 判断就 insert。**

### 模式 4：只改状态、不回退副作用

`inventory-01`（盘点冲正不回滚库存与流水）、`dining-02`（桌台置 FREE 清 `currentOrderId` 但不检查活跃订单）、`cashier-02`（日结后硬删收银记录）、`withdraw-01`（驳回覆盖已扣款单）。
改法：任何"回退/冲正/取消"操作，先列出正向路径产生的全部副作用（库存、流水、余额、凭证、缓存），逐项写回退，再改状态；回退与状态变更同一事务。

### 模式 5：同一口径存在多套实现

- 折扣核价：`marketing` 有 `calculateDiscount / calculateFullReduction / calculateBestDiscount / evaluateFullReduction` 四套，叠加/取最优/是否校验时间各不相同（`marketing-01/02`）。
- 营收口径：`report` 的 `getDailyReport` 只算 COMPLETED，`paymentTrend/timeSlot/paymentAnalysis/dishRanking` 默认不过滤（`report-01`）；`dashboard` 热销 SQL 也不过状态（`dashboard-01`）。
- 金额相等判定：退款回调 `compareTo != 0` 严格等值 vs 收银 `0.01` 容差（`payment-01`）。
- 自然日区间：`category-04` 用 `le(次日零点)` 闭区间，跨日重复计数。
改法：核价收敛为单一入口（试算与下单同源，项目里 `previewDeliveryFee` 已经是这个正确范式）；报表抽公共状态过滤片段；金额比较统一 `BigDecimal` + 显式容差常量；日期区间抽工具方法。

### 模式 6：`catch (Exception)` 降级为日志

出现位置：`member-03`（积分回退）、`groupbuy-01`（退款批次）、`subsidy-01`（餐补回充）、`delivery` 回调、各定时任务的 per-tenant `catch`、`RefundCallbackService` 的库存回补。
后果统一是"主流程认为成功、实际副作用没做、也没有人知道"。改法：失败必须落到"待补偿队列 + 告警"，而不是只 `log.error`；补偿任务要有覆盖完整性的自检（数量对账）。

### 模式 7：Controller 直接写实体 / 跨 Service 编排，绕过校验

`category-02`（`update(wrapper)` 绕过 Service 的全部校验，空更新拼出非法 SQL）、`cashier-03`（`@RequestBody` 实体直接落库）、`address-01`（Controller 内多次 Service 写调用，事务边界泄漏）、`region-02`（Controller 里"查子节点再删"，无事务）。
改法：Controller 只做参数接收与响应，校验、事务、编排下沉到 Service；写接口一律走"白名单字段 + Service 校验"而不是整实体落库。

### 模式 8：注释与实现相反，误导后续维护

- `category-01`：注释"并发竞态由唯一索引兜底"，但 `V1__baseline_schema.sql:403-417` 里 `category` 只有普通索引，`DuplicateKeyException` 分支是死代码。
- `base-01`：注释"事件发布放在事务外由 Spring 保证"，实际仍在事务内。
- `notification`：`PrinterServiceImpl` 顶部注释"禁止类级 @Transactional"，而 `NotificationServiceImpl` 恰好在发送方法上加了事务。
改法：这类注释比没有注释更危险——评审时按"注释声明"验收才发现实现不符。建议把"事务语义/并发假设"写进方法级 javadoc 时，同步给出一条可执行的验证方式（例如"由 `XxxTest` 并发用例覆盖"），否则删掉。

## 六、建议的下一步

### 6.1 本周内（P0 + 资金/权限类 P1）

按汇总表 1–20 顺序推进即可，其中三条建议合并为一次改动，因为它们同根因：

- **会话吊销**：`auth-01 + tenant-01 + user-01` 一起改（Filter 层加状态校验或写反向 Token 索引），一次解决"停用无效"的三个域。
- **提现两条**：`withdraw-01 + withdraw-02` 一起改（驳回 CAS + 确认转账对账 + FAILED 退回），这两条是同一张表的两个入口。
- **AI 权限**：`ai-01（P0）+ ai-02` 一起改（Controller 权限码 + 模板写权限），顺手把 `reveal=true` 的审计补全。

### 6.2 两周内（结构性治理，按模式而非按条）

1. **事务边界专项**：全局 grep `@Transactional`，逐个确认三件事——方法是否 public 且经代理调用、事务内是否有 HTTP/短信/推送/打印、事件是否 AFTER_COMMIT。先把 `delivery-01`、`notification-01`、`base-01` 三处改掉，形成范式再推广。
2. **权限矩阵**：把 117 个 Controller 的注解导出一张表（端点 × 注解 × 是否资金/他人数据），按"资金、账号、配置"三类补 `@RequiresPermission`。`employee` 表的查询入口统一包一层 `employeeTenantWrapper()`。
3. **唯一约束盘点**：把"业务上应唯一"的键列出来（券模板名、同用户同菜购物车、默认地址、同人同日考勤、催单限次、排班），能建唯一索引的直接建 Flyway 迁移（V18 起），不能建的改条件 UPDATE。
4. **核价与报表口径收敛**：折扣核价收敛为一个入口；报表抽公共状态过滤；金额比较统一容差常量。

### 6.3 需要业务确认后再动（21 条"疑似"）

优先确认这四条，它们决定改法方向：

- `category-03`、`recommend` 公开端点：游客的租户上下文到底由谁注入（网关/前端 storeId/域名）？这决定"匿名可访问"与"fail-closed 返回空集"是否冲突。
- `dining-02`：堂食"清台"是否允许在未结账状态下操作？决定是"禁止"还是"提示确认"。
- `kds-02`：KDS 出餐完成后，外卖订单状态由谁推进（骑手取餐 or 收银结账）？
- `common-02`：发票文件对"任一登录"开放是否符合业务对票据可见性的约定？
